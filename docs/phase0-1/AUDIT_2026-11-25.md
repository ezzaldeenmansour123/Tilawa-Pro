## 3. اختبار بحث FTS5 العربي — عملي (موثَّق)

أُعيد بناء منطق البحث حرفياً (تطبيع `build_db.py` + تعبير `db.dart::_searchExpr`) في جدول FTS5 تجريبي واختُبرت الاستعلامات. النتيجة: **بحث تلاوة أفضل بكثير من PROTOCOL، لكنه ليس سليماً تماماً.**

### ما يعمل (خلافاً لـ PROTOCOL)
الاستعلام العاري و«الـ» و«والـ» يجد النص في معظم الحالات، لأن `search_norm` في البناء يضيف الصيغة المجرَّدة لكل كلمة في الفهرس، و`_searchExpr` يضيف صيغتي «الـ» وبدونها مع بادئة `*`:
- `الرحمن` ← وجد، `والرحمن` ← وجد، `صلاة` ← وجد `الصلاة` و`والصلاة`، `الذين يؤمنون` ← وجد، `الأسبقية` ← وجد.

### العطل المؤكد 1 — استعلامات البادئات ب/ف/ل/ك تفشل
طرف الاستعلام في Dart يجرّد «الـ» فقط، ولا يجرّد و/ف/ب/ل/ك، بينما الفهرس يحتوي الصيغة المجرَّدة فقط عندما كانت في النص حرفياً:
- `بالصلاة` ← **0 نتائج** (رغم وجود «الصلاة» و«والصلاة»)، `فالصلاة` ← 0، `للصلاة` ← 0، `كالصلاة` ← 0
- `والمؤمنين` ← **0** (رغم وجود «المؤمنين»)، `للمؤمنين` ← 0، `فالمؤمنين` ← 0، `والصابرين` ← 0، `للصابرين` ← 0
- `بالغيب` نجح فقط لأن النص نفسه يحتوي «بالغيب» حرفياً؛ `فالغيب` ← 0.
- **الأثر:** المستخدم يكتب بصيغة طبيعية مشهورة («بالصلاة»، «والمؤمنين») فلا يجد شيئاً. هذا عطل بحث حقيقي، وإن كان أضيق من عطل PROTOCOL.

### العطل المؤكد 2 — تجريد أحادي الحرف يولّد إيجابيات كاذبة
`_strip_prefix` في `build_db.py` يجرّد و/ف/ب/ل/ك من **أي** كلمة دون قاموس:
- `كانت` ← تُفهرس أيضاً كـ `انت`، فيجد البحث عن `انت` آية «كانت» خطأً.
- `بسم` ← تُفهرس كـ `سم`، `كتابا` ← تُفهرس كـ `تابا`. البحث عن `سم` أو `تابا` يعيد نتائج خاطئة وتلوّث ترتيب النتائج.

### حدود أخرى موثَّقة
- بحث التفاسير **ليس FTS أصلاً**: `_searchTafsirSync` يستخدم `LIKE %...%` على النص الخام (مسح كامل، بلا ترتيب أهمية، حد 30) — بطيء ويُفوّت صيغ البادئات والهمزة.
- لا بحث بالجذر، لا بحث بالموضوع، لا بحث بالإنجليزية، لا معاني كلمات ولا إعراب (غير موجودين في DB: لا جدول `words` ولا `roots`).
- التطبيع نفسه سليم في الأساس: ألف مقصورة ← ياء، ة ← هـ، الهمزات ← ألف، التشكيل يُزال، والألف الخنجرية تُعامل كحرف (الصلوة ← الصلاة) — وهذا تصميم صحيح ويجب الحفاظ عليه.

### الإصلاح المقترح (Phase 0 — مسودة، لم تُطبَّق بعد، تحتاج اختبار Flutter)
1. طبّق تجريد البادئات نفسه على طرف الاستعلام في Dart (`_searchExpr` و`_askSync` و`_relatedSync`): لكل مصطلح ولّد {الأصل، مجرَّد وال/فال/بال/لل/كال، مجرَّد ال، مجرَّد و/ف/ب/ل/ك}.
2. قيّد التجريد أحادي الحرف: لا تجرّد و/ف/ب/ل/ك إلا إذا كان الباقي يبدأ بـ «ال» أو طوله ≥ 5 أحرف — يمنع `انت ← كانت` و`سم ← بسم`، ويبقي `والصلاة ← الصلاة`.
3. انقل بحث التفاسير إلى عمود FTS نفسه (العمود `tafsir` موجود في `ayahs_fts` أصلاً) بدل `LIKE`.
4. اختبارات انحدار إلزامية قبل الدمج: `بالصلاة`، `والمؤمنين`، `فالغيب`، `للصابرين` يجب أن تعيد نتائج؛ و`انت` و`سم` و`تابا` يجب ألا تعيد «كانت/بسم/كتابا».

## 5. الأخطاء والمخاطر (مرتبة بالخطورة)

### حرجة
1. **APK موقَّع بمفتاح debug** (README يقرّ بذلك). أي شخص يستطيع توقيع تحديث يبدو صادراً عن التطبيق؛ وGoogle Play يرفضه. لا يوجد keystore ولا `key.properties` (وهذا صحيح — يجب ألا يكونا في المستودع أبداً)؛ الحل: keystore خارج المستودع + أسرار GitHub Actions، و**لا تغيير للتوقيع دون موافقة المستخدم** (قاعدة 12 في المهمة).
2. **لا اختبارات إطلاقاً، والـ CI يحذف `test/`.** أي إعادة بناء قد تكسر المصحف بصمت. `build_db.py` وحده يتحقق من الأعداد — لكن لا اختبار Dart واحد.
3. **لا مجلد `android/` في المستودع.** كل بناء يعتمد على `flutter create` في CI + تعديلات نصية هشّة على Manifest/Gradle (تعتمد على نصوص حرفية مثل `'} \n\nkotlin {'`). أي تحديث Flutter قد يكسر البناء دون أن يلاحظ أحد محلياً.

### عالية
4. **بحث FTS معطوب جزئياً** (§3): استعلامات البادئات تفشل، وإيجابيات كاذبة من التجريد الأعمى. قابل للإصلاح في Phase 0 دون تغيير البنية.

2. **تطبيقك يخالف شروط QF ضمنياً إن خزّن تفاسيرها:** `onlineTafsir` في `db.dart` يحفظ نصوص Quran.com API محلياً دون حد زمني («cached»)، بينما شروط QF تسمح بتخزين ≤ أسبوع ما لم يُصرَّح كتابةً. التخزين المؤقت الحالي **يحتاج مراجعة قانونية** — إما حد 7 أيام مع إعادة جلب، أو التوقف عن الاعتماد على QF للتخزين الدائم والانتقال إلى QuranLab بعد فحص تراخيصه.

### 7.2 نظام الحزم الاختيارية السبع (الحجم تقديري — يُؤكَّد عند بناء كل حزمة)

| الحزمة | المحتوى | الحجم التقديري | في APK؟ |
|---|---|---|---|
| 0. الأساسية | Flutter + DB الحالية (قرآن + 3 تفاسير) + أميري | **50–70 MB** (الهدف بعد تقسيم المعالجات ≈ 48 MB) | نعم |
| 1. صفحات المصحف | تخطيط صفحات نصي من DB (رخيص)؛ أو صور 604 إن رُخِّصت | نصي: <1 MB؛ صور: **يُقدَّر بعد الترخيص (عشرات MB)** | لا — عند الطلب |
| 2. القراء | لكل قارئ: سورة ≈ 5–30 MB حسب الطول والجودة؛ قرآن كامل ≈ 300–900 MB حسب الجودة | يُعرض قبل التنزيل | لا — عند الطلب |
| 3. التفاسير | ابن كثير/الطبري/القرطبي، كل تفسير حزمة مستقلة | كل واحد **≈ 10–25 MB نص + FTS** (يُؤكَّد) | لا — عند الطلب |
| 4. نموذج التسميع | yazinsai خفيف 25 MB / كامل 68 MB (+ ONNX Runtime) | **25–68 MB** | لا — عند الطلب، مع حالة «غير مثبَّت» |
| 5. الدروس | تجويد + نورانية + أطفال (نص + صوت أمثلة) | **≈ 5–20 MB** | لا — عند الطلب |
| 6. الترجمات | Sahih International + لغات أخرى، كل لغة حزمة | كل لغة **≈ 1–3 MB** | لا — عند الطلب |

**قواعد الحزم:** عرض الحجم قبل التنزيل؛ إيقاف/استكمال؛ تحقق SHA-256؛ عرض المساحة المستخدمة والمتبقية؛ لا حذف لمحتوى مثبَّت عند تحديث التطبيق؛ لا تنزيل تلقائي إطلاقاً.

### 7.3 ترحيل قاعدة البيانات دون فقد بيانات المستخدم
1. جدول `user_meta(key, value)` فيه `schema_version` (يبدأ 1) + `lib_sha`.
2. كل ترحيل مرقَّم ومكتوب كدالة `migrate_1_to_2()` مع اختبار وحدة؛ يُطبَّق مرة واحدة عند أول فتح بعد التحديث، قبل أي قراءة.
3. نقل بيانات المستخدم (مفضلة/ملاحظات/وسوم/سجل/ختمة) من SharedPreferences إلى جداول SQLite في الترحيل الأول، مع نسخة احتياطية من ملف JSON القديم قبل الحذف، وتصدير/استيراد JSON يملكه المستخدم.
4. `needsUpdate()` الموجود يُبقي سلوكه: مقارنة SHA للـ DB المدمجة بالمثبتة، واستبدال ذري (ملف مؤقت + إعادة تسمية) فقط بعد تحقق SHA.

### 7.4 Offline-First (غير قابل للتنازل)
- التشغيل الأول دون إنترنت، بلا حساب، بلا رسالة اتصال.
- الاتصال فقط عند: ضغطة تنزيل صريحة من المستخدم، أو طلب تحديث، أو بحث في محتوى غير محلي (بموافقة).
- لا تحليلات خارجية، لا تتبع، لا رفع صوت، لا STT سحابي، لا API خارجي للبحث/التفسير اليومي، لا تحديثات/تنزيلات تلقائية.
- مؤشر في الإعدادات: حالة الاتصال، المحتوى المحلي المتوفر، النماذج المثبتة، مساحة التنزيلات، آخر تحديث — بلا إزعاج برسائل انقطاع ما دامت الوظيفة محلية.
- اختبار العزل: Wi-Fi وبيانات مغلقة → المصحف والبحث والتفسير المحمل والصوت المحمل والتسميع والحفظ والملاحظات تعمل طبيعياً؛ ويُفحص عدم وجود اتصالات صادرة غير مصرح بها.

## 9. العوائق التي تحتاج قرار المستخدم

1. **ترخيص yazinsai/tilawa (النموذج):** هل يُسمح باستخدامه في منتج مجاني؟ وهل قيد «No-Profit» يمنع أي ميزة مدفوعة مستقبلاً؟ — القرار: دمج / بديل / تأجيل التسميع إلى Phase 3.
2. **القرّاء الناقصون:** مصطفى إسماعيل جزئي (لا يُعرض كمكتمل)، إدريس أبكر غير موجود، والسديس+الشريم المشترك غير موجود نقياً — القرار: الإعلان بـ 17 قارئاً كاملاً، أو اختيار بديلين موثَّقين من قائمة EveryAyah.
3. **صور صفحات مصحف المدينة:** هل يوجد مصدر مرخَّص لإعادة التوزيع؟ إن لم يوجد، القرار: تخطيط نصي للصفحات (آمن وموجود في DB) دون صور.
4. **التفاسير الكبيرة دون إنترنت:** هل شروط Quran.com تسمح بتخزينها كحزم؟ إن لم تسمح، القرار: تبقى متصلة عند الطلب مع تخزين مؤقت.
5. **التوقيع:** إنشاء keystore إصدار جديد خارج المستودع (المفتاح الحالي debug فقط) — القرار: إنشاء مفتاح جديد بموافقة المستخدم وحفظه خارج GitHub، مع العلم أن تغيير التوقيع يعني أن التثبيتات الحالية لا تُحدَّث تلقائياً بل تُعاد تثبيتها.
6. **ترخيص كود Tilawa نفسه:** لا LICENSE في المستودع — القرار: MIT للكود (يُقترح) مع إبقاء نسبة Tanzil للمحتوى.
7. **حجم نموذج التسميع (25–68 MB):** تنزيل اختياري عند الطلب — القرار: تأكيد أن المستخدمين الجدد لا يُجبَرون عليه.
8. **معرّف القرطبي 90 غير موثَّق + تخزين QF:** أعيدوا التحقق من 90 في `/resources/tafsirs`، وقرروا مصير التخزين المؤقت الحالي لتفاسير Quran.com (حد 7 أيام أو إيقاف) — انظر §6.4.
9. **PoC محرك التسميع في Flutter:** لا مسار رسمي؛ القرار: هل يُستثمر 2–3 أسابيع في إثبات جدوى WebView/إعادة تنفيذ Dart قبل الالتزام بـ Phase 3، أم يُؤجَّل التسميع؟

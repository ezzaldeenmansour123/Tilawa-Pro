## 1. الواقع الحالي — موثَّق من الكود

### 1.1 مفاتيح SharedPreferences المستخدمة فعلاً

**إعدادات التطبيق** — `lib/main.dart`، صنف `AppSettings` (الأسطر 46–107).
تبقى في SharedPreferences ولا تُرحَّل (صغيرة، غير علائقية، وتعمل أصلاً):

| المفتاح | النوع | الافتراضي | المعنى |
|---|---|---|---|
| `mode` | int | `0` (system) | `ThemeMode` |
| `font` | double | `26` | حجم الخط |
| `amiri` | bool | `true` | خط أميري |
| `reciter` | String | `'afasy'` | معرّف القارئ الحالي |
| `reminder` | bool | `false` | التذكير اليومي |
| `rem_hour` / `rem_min` | int | `7` / `0` | وقت التذكير |
| `wird_q` | int | `1` | مقدار الورد (1 ربع حزب، 4 حزب، 8 جزء) |

**بيانات المستخدم** — `lib/main.dart`، صنف `UserData` (الأسطر 111–203). هذه التي تُرحَّل:

| المفتاح | النوع في prefs | البنية الفعلية | ملاحظات سلوكية موثَّقة |
|---|---|---|---|
| `favs` | StringList | `["2","255","7"]` — معرّفات آيات عالمية (int) كسلاسل، **بترتيب الإضافة** | `toggle()` يمنع التكرار داخل التطبيق؛ وعند إلغاء المفضلة يُحذف وسمها (`tags.remove(id)`) **ولا تُحذف ملاحظتها** |
| `history` | StringList | `["255","2","7"]` — **الأحدث أولاً**، بلا تكرار، **سقف 100** (`touch()` يزيل ثم يدرج في 0 ويقصّ ما بعد 100) | |
| `tags` | String (JSON) | `{"2":"تجويد","7":"حفظ"}` — **وسم واحد لكل آية** (Map<int,String>) | يُقرأ بـ `jsonDecode` في `_readMap` (سطر 120) — JSON معطوب يُسقط التحميل كله اليوم |
| `notes` | String (JSON) | `{"2":"ملاحظة…","255":"…"}` — **ملاحظة واحدة لكل آية** | مستقلة عن المفضلة: تبقى بعد إلغاء التفضيل |
| `khatmah_q` | int | `1..240`، الافتراضي `1` | `completeWird()` يضيف `wird_q` ويقيّد إلى `241` — **القيمة 241 تعني «الختمة مكتملة»** وتُحفظ كما هي |
| `warsh_ready` | bool | الافتراضي `false` | علم أن حزمة ورش (ملف `warsh.json` المنفصل) جاهزة |
| `fav_reciters` | StringList | `["afasy","husary"]` — معرّفات قرّاء | |
| `lib_sha` | String | SHA-256 سداسي عشري (64 حرفاً) للمكتبة المثبتة | يُكتب في `Repo.install()` (db.dart:372) ويُقرأ في `needsUpdate()` (db.dart:378) — **ليس بيانات مستخدم، بل بصمة مكتبة** |

**لا مفاتيح أخرى.** فحص شامل لـ `getString/getInt/getBool/getDouble/getStringList` في
`lib/main.dart` و`lib/db.dart` لم يجد غير ما سبق.

### 1.2 مخطط `quran.db` الحالي — موثَّق من `tools/build_db.py:205–214, 331–333`

ملف المكتبة المدمجة (40.2 MB خام)، يُبنى في CI من HuggingFace ويُنسخ إلى
`getApplicationSupportDirectory()/quran.db`:

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT);
-- الصفوف: source, quran_commit, tafsir_commit, built, total='6236', surahs='114', credits

CREATE TABLE surahs(id INTEGER PRIMARY KEY, name_ar TEXT, name_short TEXT,
                    name_en TEXT, revelation TEXT, ayah_count INTEGER, juz_start INTEGER);

CREATE TABLE ayahs(id INTEGER PRIMARY KEY, surah INTEGER, ayah INTEGER, text TEXT,
                   juz INTEGER, hizb INTEGER, quarter INTEGER, page INTEGER, sajda INTEGER);

CREATE TABLE tafsir(surah INTEGER, ayah INTEGER, source TEXT, text TEXT,
                    PRIMARY KEY(surah, ayah, source));

CREATE TABLE ijaz(id INTEGER PRIMARY KEY, title TEXT, ayah_ref TEXT, surah INTEGER,
                  ayah INTEGER, text TEXT, source TEXT);

CREATE VIRTUAL TABLE ayahs_fts USING fts5(norm, tafsir,
                    tokenize='unicode61 remove_diacritics 0');

CREATE INDEX idx_a_surah   ON ayahs(surah, ayah);
CREATE INDEX idx_a_quarter ON ayahs(quarter);
CREATE INDEX idx_t_ayah    ON tafsir(surah, ayah);
```

حقائق تصميمية مهمة:
- **لا يوجد جدول `user_meta` في `quran.db`** — التدقيق والخطة يفترضانه، لكن الكود الحالي بلا أي جدول بيانات مستخدم في SQLite.
- **لا مفاتيح أجنبية (FOREIGN KEY) في أي جدول** — العلاقات ضمنية عبر `ayahs.id`.
- `quran.db` **يُستبدل كاملاً عند تحديث المكتبة** (انظر §4) — لذلك **لا يجوز إطلاقاً وضع بيانات المستخدم داخله**؛ أي جدول مستخدم فيه سيُمحى مع أول تحديث مكتبة.
- ملف ثانٍ منفصل موجود أصلاً: `cache.db` في المجلد نفسه، فيه جدول `online_tafsir(surah, ayah, source, text, fetched_at, PRIMARY KEY(surah, ayah, source))` يُنشأ كسولاً في `onlineTafsir()` (db.dart:479). هو ذاكرة تخزين مؤقت لمحتوى متصل، لا بيانات مستخدم — **يبقى كما هو** (مع ملاحظة: شروط Quran.com تسمح بتخزين ≤ 7 أيام؛ `fetched_at` موجود أصلاً فيسمح بفرض الحد لاحقاً — خارج نطاق هذه المهمة).
- `Repo.open()` (db.dart:425) يفتح `quran.db` **للقراءة فقط** — ملف بيانات المستخدم يحتاج مقبضاً منفصلاً للقراءة والكتابة.

### 1.3 سلوك `install()` و`needsUpdate()` الحالي — موثَّق (db.dart:345–390)

- `install()`: يكتب الأصول إلى `quran.db.tmp` بمقاطع 1 MB → يحسب SHA-256 للملف المؤقت في Isolate → يقارنه بـ `assets/quran.db.sha256` → عند المطابقة يعيد التسمية إلى `quran.db` → يعيد التحقق بـ `isInstalled()` (الملف ≥ 1 MB وعدد الآيات = 6236) وإلا يحذف ويرمي استثناءً → يحفظ `lib_sha` في prefs. **عند عدم المطابقة يُحذف المؤقت ويبقى المثبت القديم سليماً.**
- `needsUpdate()`: يقارن SHA المدمج مع prefs `lib_sha` فقط — **لا يفحص محتوى الملف المثبت نفسه** (لذلك `verifyHash()` و`quickCheck()` موجودان كفحصين منفصلين في واجهة المكتبة).

## 2. مخطط الترحيل — مصمَّم

### 2.1 القرار الأساسي: ملف `user.db` منفصل

| الملف | المحتوى | يُستبدل عند تحديث المكتبة؟ |
|---|---|---|
| `quran.db` | نص القرآن + التفاسير المدمجة + الإعجاز + FTS (كما هو، بلا تغيير) | نعم — ذرياً |
| `cache.db` | `online_tafsir` المؤقت (كما هو) | لا |
| **`user.db` (جديد)** | `user_meta` + كل جداول بيانات المستخدم (§2.2) | **لا أبداً** |
| `warsh.json` | حزمة ورش (كما هو) | لا |

**لماذا ملف منفصل لا جدول داخل `quran.db`؟** لأن `install()` يستبدل `quran.db` كاملاً بإعادة تسمية؛ أي بيانات مستخدم فيه ستُفقد بصمت مع أول تحديث مكتبة. وملف منفصل يجعل النسخ الاحتياطي/الاستعادة لبيانات المستخدم مستقلاً عن المكتبة (40 MB)، ويجعل فتح `quran.db` للقراءة فقط غير متأثر.

### 2.2 مخطط `user.db` — الإصدار 1

```sql
CREATE TABLE user_meta(key TEXT PRIMARY KEY, value TEXT);
-- schema_version   = '1'   (يبدأ 1 عند إنشاء user.db جديد — انظر §2.3)
-- lib_sha          = '<sha256 للمكتبة المثبتة>'  (ينتقل هنا من prefs 'lib_sha')
-- migrated_from_prefs = '1' | '0'   (هل جاءت البيانات من SharedPreferences؟)
-- migrated_at      = '<ISO-8601 لحظة الترحيل>'
-- prefs_backup     = '<اسم ملف النسخة الاحتياطية>'

CREATE TABLE favorites(
  ayah_id    INTEGER PRIMARY KEY,   -- معرّف الآية العالمي 1..6236
  position   INTEGER NOT NULL,      -- ترتيب الإضافة (يحفظ ترتيب قائمة favs)
  created_at TEXT NOT NULL           -- ISO-8601؛ للصفوف المهاجَرة = لحظة الترحيل
);
CREATE INDEX idx_fav_position ON favorites(position);

CREATE TABLE notes(
  ayah_id    INTEGER PRIMARY KEY,   -- ملاحظة واحدة لكل آية (كما في التطبيق اليوم)
  body       TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE tags(
  ayah_id    INTEGER PRIMARY KEY,   -- وسم واحد لكل آية (كما في التطبيق اليوم)
  tag        TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
-- ملاحظة تصميمية: إن أُريد لاحقاً أكثر من وسم للآية، يكون ذلك ترحيلاً
-- لاحقاً (migrate_1_to_2) يحوّل هذا الجدول إلى علاقة كثير-لكثير؛
-- لا يُغيَّر شكل البيانات في الترحيل الأول.

CREATE TABLE history(
  ayah_id    INTEGER PRIMARY KEY,
  position   INTEGER NOT NULL,      -- 0 = الأحدث (يحفظ ترتيب قائمة history)
  visited_at TEXT NOT NULL           -- للصفوف المهاجَرة = لحظة الترحيل
);
CREATE INDEX idx_hist_position ON history(position);

CREATE TABLE khatmah(
  id         INTEGER PRIMARY KEY CHECK(id = 1),  -- صف وحيد (singleton)
  quarter    INTEGER NOT NULL CHECK(quarter BETWEEN 1 AND 241),
  updated_at TEXT NOT NULL
);
-- القيمة 241 = الختمة مكتملة (سلوك completeWird الحالي) وتُحفظ كما هي.

CREATE TABLE fav_reciters(
  reciter_id TEXT PRIMARY KEY,
  position   INTEGER NOT NULL       -- يحفظ ترتيب القائمة
);

CREATE TABLE flags(
  key   TEXT PRIMARY KEY,           -- مثال: 'warsh_ready'
  value TEXT NOT NULL               -- '1' / '0'
);
```

**لا مفاتيح أجنبية عبر الملفات** (مستحيل تقنياً بين `user.db` و`quran.db`) — سلامة معرّفات الآيات تُفرض بالتحقق عند الكتابة/الترحيل مقابل `ayahs.id` في `quran.db` (§3.3)، لا بقيد قاعدة بيانات.

**الصفوف المهاجَرة بلا طوابع زمنية أصلية:** prefs لا تخزّن أي وقت؛ تُملأ `created_at/updated_at/visited_at` بلحظة الترحيل، ويُدوَّن ذلك في سجل الترحيل (§3.5).

### 2.3 ترقيم الإصدارات والترحيلات

- **الإصدار 0 (ضمني):** لا يوجد `user.db`؛ بيانات المستخدم في SharedPreferences (الحالة الحالية لكل مستخدم مثبَّت). لا يُكتب الرقم 0 في أي مكان — غياب الملف هو العلامة.
- **الإصدار 1:** `user.db` موجود بالمخطط أعلاه. التثبيت الجديد ينشئه مباشرة بالإصدار 1 (بلا بيانات مهاجَرة، `migrated_from_prefs='0'`).
- **`migrate_0_to_1()`:** ترحيل الإرث الوحيد الذي ينقل prefs → SQLite (§3).
- **`migrate_1_to_2()` وما بعدها:** محجوزة للتغييرات المستقبلية (مثال: وسوم متعددة للآية، سجل استماع، خطط حفظ). كل ترحيل دالة مستقلة مرقَّمة مع اختبار وحدة، وتُطبَّق بالتسلسل مرة واحدة عند أول فتح بعد التحديث، **قبل أي قراءة لبيانات المستخدم** (قبل `UserData.load()` وقبل `Repo.open()`).

### 2.4 أين يعيش الكود (مقترح، يطابق خطة Phase 0)

```
lib/data/migrations.dart   # جديد: runMigrations() + migrate_0_to_1() + migrate_1_to_2()…
lib/data/user_db.dart      # جديد: فتح user.db (قراءة/كتابة) + دوال CRUD لبيانات المستخدم
lib/data/db.dart           # الحالي: يبقى للمكتبة فقط؛ needsUpdate()/install() تقرأ
                           # lib_sha من user_meta مع رجوع احتياطي إلى prefs قبل الترحيل
lib/core/user_data.dart    # UserData بعد التقسيم: تقرأ/تكتب في user.db بدل prefs
test/migration_test.dart   # جديد: اختبارات الترحيل في Flutter (انظر §7)
```

لا حزمة جديدة مطلوبة: `sqlite3` (المستخدمة أصلاً في `db.dart`) تكفي لفتح `user.db` للقراءة والكتابة.

## 3. خطوات الترحيل `migrate_0_to_1()` — مصمَّمة

**ترتيب التشغيل عند الإقلاع (بعد تقسيم `main.dart`):**
1. تأكيد تثبيت المكتبة (`install()` إن لزم — يكتب `lib_sha` في prefs إن لم يوجد `user.db` بعد، وفي `user_meta` إن وُجد).
2. `runMigrations()` — قبل أي `UserData.load()`.
3. فتح `Repo` (قراءة فقط) وتحميل `UserData` من `user.db`.

### 3.1 الخطوات بالترتيب (كلها داخل `migrate_0_to_1()`)

| # | الخطوة | التفصيل |
|---|---|---|
| 1 | **اقرأ prefs الخام إلى الذاكرة** | اقرأ المفاتيح الثمانية المُرحَّلة كقيم خام دون تحليل: `favs, history, tags, notes, khatmah_q, warsh_ready, fav_reciters, lib_sha`. لا تحذف شيئاً بعد. |
| 2 | **اكتب النسخة الاحتياطية أولاً** | ملف `backups/prefs_backup_YYYYMMDD_HHMMSS.json` في مجلد دعم التطبيق (§4.1)، يحوي القيم الخام حرفياً + `format_version` + طابعاً زمنياً + SHA-256 للملف نفسه. **أعد قراءة الملف وقارنه بالقيم في الذاكرة؛ إن فشلت المطابقة أو الكتابة (قرص ممتلئ مثلاً) أوقف الترحيل كاملاً** — التطبيق يستمر على مسار prefs القديم كأن شيئاً لم يكن. |
| 3 | **حلّل وتحقّق** | لكل قائمة: `int.parse` لكل عنصر؛ لكل خريطة JSON: `jsonDecode` ثم `int.parse` للمفاتيح. **كل قيمة فاسدة تُعزل في الحجر الصحي** (§3.3) ولا توقف الترحيل. تحقق من كل `ayah_id` مقابل `SELECT id FROM ayahs` في `quran.db` (قراءة فقط). تحقق من `khatmah_q` ضمن 1..241. |
| 4 | **أنشئ `user.db` في معاملة واحدة** | `BEGIN IMMEDIATE` → نفّذ مخطط §2.2 → أدخل الصفوف مع `position` الحافظ للترتيب → اكتب `user_meta` (`schema_version='1'`, `lib_sha` من prefs، `migrated_from_prefs='1'`, `migrated_at`, `prefs_backup`) → `COMMIT`. عند أي استثناء: `ROLLBACK` واحذف الملف، وأعد رمي الخطأ. |
| 5 | **تحقّق سجلاً بسجل قبل أي حذف** | أعد قراءة كل جدول من `user.db` وقارنه بالقيم المحللة في الذاكرة: الأعداد + ترتيب `position` + محتوى كل وسم/ملاحظة + `khatmah_q` + `lib_sha` + `PRAGMA quick_check = ok`. **أي عدم تطابق = فشل ترحيل: احذف `user.db`، وأبقِ prefs سليمة، وسجّل الفشل.** |
| 6 | **نظّف prefs فقط بعد نجاح التحقق** | احذف المفاتيح الثمانية المُرحَّلة فقط (`favs, history, tags, notes, khatmah_q, warsh_ready, fav_reciters, lib_sha`). **مفاتيح الإعدادات الثمانية تبقى** (`mode, font, amiri, reciter, reminder, rem_hour, rem_min, wird_q`). |
| 7 | **سجّل** | أدخل سجل ترحيل في `user_meta` (`migration_log` — أو ملف `migration.log` بجانب النسخة): الأعداد المدخَلة والمُعزَلة لكل جدول + أسباب العزل + زمن التنفيذ. |

### 3.2 خصائص الأمان المضمّنة في التصميم

- **النسخة الاحتياطية قبل أي كتابة مدمّرة** (الخطوة 2 قبل الخطوة 6).
- **المعاملة الواحدة** تجعل إنشاء `user.db` ذرياً: إما كامل أو غير موجود.
- **التحقق قبل الحذف** (الخطوة 5 قبل 6) يمنع فقدان أي سجل صالح.
- **خامل (idempotent):** إعادة التشغيل بعد أي تعطل آمنة (§5).
- **مسار رجوع قديم:** إن فشل الترحيل كله، يبقى كود القراءة من prefs هو المسار المستخدم، ويُعاد الترحيل في الإقلاع التالي — بلا أي فقد.

### 3.3 قواعد الحجر الصحي (quarantine)

| الحالة | الإجراء |
|---|---|
| عنصر قائمة ليس عدداً (`"abc"`) | يُعزل، ويُدوَّن سببه `not-an-int` |
| `ayah_id` غير موجود في `quran.db` (مثال `99999`) | يُعزل، سببه `ayah-not-in-quran-db` |
| تكرار في القائمة (مثال `"2"` مرتين في `favs`) | يُحفظ أول ظهور فقط، ويُدوَّن التكرار |
| `tags` أو `notes` بسلسلة JSON معطوبة كلياً | **الخريطة كلها تُعزل** (لا إدخال جزئي منها)، والسلسلة الخام محفوظة حرفياً في النسخة الاحتياطية؛ باقي المفاتيح تُرحَّل طبيعياً |
| `khatmah_q` خارج 1..241 أو ليس عدداً | يُعزل ويُستخدم الافتراضي `1`، ويُدوَّن ذلك |
| وسم/ملاحظة لآية غير موجودة في `quran.db` | تُعزل وحدها؛ باقي الخريطة يُرحَّل |

كل سجل معزول يبقى قابلاً للاستعادة يدوياً من ملف النسخة الاحتياطية (§4.1) — **لا يُحذف أي بيان أصلي أبداً في خطوة الترحيل**.

### 3.4 ماذا عن `lib_sha` و`needsUpdate()` بعد الترحيل؟

- المصدر الوحيد للحقيقة بعد الترحيل: `user_meta.lib_sha` في `user.db`.
- `needsUpdate()`: يقرأ `user_meta.lib_sha`؛ وإن لم يوجد `user.db` بعد (قبل الترحيل) يرجع إلى prefs `lib_sha` — هذا الرجوع ضروري لأن `install()` قد يعمل قبل أول ترحيل.
- `install()` بعد الترحيل: يكتب `lib_sha` الجديد في `user_meta` (لا في prefs). قبل الترحيل: يكتبه في prefs كاليوم، فينقله الترحيل إلى `user_meta` في الخطوة 4.
- `quran.db` نفسه **لا يتغير مخططه إطلاقاً** — جدول `meta` فيه يبقى كما هو.

### 3.5 سجل الترحيل (مثال)

  "inserted": {"favorites": 3, "history": 3, "tags": 2, "notes": 2,

## 4. النسخ الاحتياطي والاستعادة — مصمَّم

### 4.1 النسخة الاحتياطية التلقائية (قبل الترحيل)

- **المسار:** `getApplicationSupportDirectory()/backups/prefs_backup_YYYYMMDD_HHMMSS.json`
  (المجلد نفسه الذي فيه `quran.db` و`user.db` و`cache.db`).
- **المحتوى:** القيم الخام للمفاتيح الثمانية حرفياً (بما فيها القيم التالفة)،
  إضافة إلى `format: "tilawa-prefs-backup"`, `format_version: 1`, الطابع الزمني، وSHA-256 للملف.
- **القاعدة:** تُكتب وتُتحقق بإعادة القراءة **قبل** أي حذف من prefs (§3.1 خطوة 2).
- **الاحتفاظ:** تُحفظ آخر 3 نسخ تلقائية؛ الأقدم يُحذف عند إنشاء الرابعة (لا تُحذف النسخة الوحيدة أبداً إن كانت هي الوحيدة).
- **حدّ مهم وصادق:** هذه النسخة تعيش داخل بيانات التطبيق — تحمي من **أخطاء الترحيل**، لا من **إلغاء التثبيت أو مسح بيانات التطبيق** (النظام يحذفها معه). الحماية من إلغاء التثبيت هي التصدير الذي يملكه المستخدم (§4.2) فقط.

### 4.2 تصدير/استيراد JSON يملكه المستخدم (جديد — في الإعدادات)

**التصدير** (زر «تصدير بياناتي»): يولّد ملف `tilawa-backup-YYYYMMDD.json` يشاركه/يحفظه المستخدم بنفسه:

```json
{
  "format": "tilawa-user-export", "format_version": 1,
  "exported_at": "2026-11-25T05:30:00+03:00",
  "data": {
    "favorites": [2, 255, 7],
    "history": [255, 2, 7],
    "tags": {"2": "تجويد", "7": "حفظ"},
    "notes": {"2": "ملاحظة أولى", "255": "ملاحظة ثانية"},
    "khatmah_q": 42,
    "fav_reciters": ["afasy", "husary"],
    "warsh_ready": true
  }
}
```

- الترتيب محفوظ (المفضلة بترتيب الإضافة، السجل الأحدث أولاً).
- لا يشمل الإعدادات ولا `lib_sha` (بصمة مكتبة لا بيانات مستخدم).

**الاستيراد** (زر «استيراد نسخة احتياطية»):
1. اختر الملف → تحقق من `format` و`format_version` (ارفض غير المطابق برسالة واضحة).
2. **تحقق مسبق (dry-run):** كل `ayah_id` موجود في `quran.db`، و`khatmah_q` ضمن 1..241، والأنواع صحيحة. اعرض للمستخدم عدد السجلات الصالحة والمعزولة **قبل** أي كتابة، واطلب تأكيداً.
3. **نسخة احتياطية تلقائية قبل الاستبدال:** صدّر الحالة الحالية إلى `backups/pre-import_YYYYMMDD_HHMMSS.json` أولاً.
4. **استبدال ذري:** اكتب `user.db` الجديد كاملاً في `user.db.tmp` → `PRAGMA quick_check` + تحقق من الأعداد → `os.replace` (إعادة تسمية) فوق `user.db` → أعد فتح المقبض. **الاستيراد يستبدل بيانات المستخدم الحالية كلياً** (لا دمج) — وهذا مذكور صراحة في واجهة التأكيد.
5. عند أي فشل قبل إعادة التسمية: يُحذف المؤقت، وتبقى `user.db` القديمة سليمة.

### 4.3 الاستبدال الذري للمكتبة `quran.db` (موجود — يُبقى كما هو)

السلوك الحالي في `Repo.install()` (db.dart:345–374) **صحيح ويُحافَظ عليه دون تغيير**:
`quran.db.tmp` (كتابة بمقاطع 1 MB) → SHA-256 للمؤقت مقابل `assets/quran.db.sha256` → عند المطابقة `rename` إلى `quran.db` → إعادة تحقق `isInstalled()` (6236 آية) → عند أي فشل يُحذف المؤقت وتُرمى استثناء وتبقى المكتبة القديمة.
**قاعدة إضافية واحدة:** `install()` لا يمسّ `user.db` ولا `cache.db` ولا `warsh.json` أبداً — لا حذف لمحتوى مثبَّت عند تحديث التطبيق (PLAN §3.2).

## 5. المخاطر: ماذا يحدث إن فشل الترحيل في المنتصف؟ — مصمَّم

| لحظة الفشل | حالة البيانات | ماذا يحدث عند الإقلاع التالي | كيف تُستعاد البيانات |
|---|---|---|---|
| قبل كتابة النسخة الاحتياطية (قرص ممتلئ، عطل) | prefs سليمة؛ لا `user.db` | يُعاد الترحيل من الصفر | لا شيء مفقود أصلاً |
| أثناء كتابة النسخة / فشل إعادة قراءتها | prefs سليمة؛ لا `user.db` | يُعاد الترحيل؛ التطبيق يعمل على prefs | لا شيء مفقود |
| أثناء المعاملة (`BEGIN … COMMIT`) | prefs سليمة؛ `user.db` غير مكتمل أو غائب | `ROLLBACK` تلقائي؛ الملف الناقص يُحذف؛ يُعاد الترحيل | لا شيء مفقود |
| **بعد `COMMIT` وقبل تنظيف prefs** (تعطل/نفاد بطارية) | **`user.db` مكتمل v1 + prefs ما زالت كاملة** | الترحيل يكتشف `schema_version='1'` + `migrated_from_prefs='1'`، يتحقق من الأعداد مقابل prefs، ثم **يكمل تنظيف prefs فقط** — بلا إعادة إدخال وبلا تكرار (المفاتيح الأساسية تمنعه) | لا شيء مفقود؛ التنظيف يُستكمل تلقائياً |
| أثناء تنظيف prefs (بين حذف مفتاح وآخر) | `user.db` مكتمل وموثَّق | المفاتيح المتبقية تُتجاهل (الكود الجديد لا يقرؤها أبداً) وتُحذف في الإقلاع التالي | لا شيء مفقود |
| JSON معطوب في `tags`/`notes` | باقي المفاتيح تُرحَّل؛ الخريطة المعطوبة في الحجر | الترحيل يكمل؛ يُعرض للمستخدم عدد السجلات المعزولة | السلسلة الخام في النسخة الاحتياطية — تُستعاد يدوياً أو بإعادة إدخال |
| `ayah_id` غير موجود في `quran.db` | يُعزل ويُدوَّن سببه | الترحيل يكمل | في النسخة الاحتياطية + سجل الترحيل |
| فساد `user.db` لاحقاً (بعد أشهر) | `PRAGMA quick_check` يفشل عند الفتح | التطبيق يعرض خطأً صريحاً ولا يكتب فوق الملف التالف؛ الاستعادة من آخر تصدير للمستخدم (§4.2) أو من نسخة prefs (§4.1) إن وُجدت | تصدير المستخدم أو نسخة prefs |
| إلغاء التثبيت / مسح بيانات التطبيق | **كل شيء يُحذف** (prefs + `user.db` + النسخ التلقائية) | تثبيت جديد يبدأ فارغاً | **تصدير المستخدم (§4.2) فقط** — النسخ التلقائية لا تحمي من هذا |

**قاعدة ذهبية في كل الحالات:** لا خطوة في الترحيل تحذف مصدراً قبل التحقق من سلامة الهدف.
الترتيب دائماً: **نسخة احتياطية → كتابة الهدف في معاملة → تحقق سجلاً بسجل → حذف المصدر**.

## 8. ملخص القرارات التصميمية (للمراجعة)

### الأثر إن أُنشئ keystore جديد — إعادة تثبيت إجبارية

Android يطابق التوقيع عند التحديث؛ توقيع جديد ≠ توقيع debug القديم، فيفشل التحديث (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`). التثبيتات الحالية يجب **إلغاء تثبيتها أولاً ثم تثبيت النسخة الجديدة**، وإلغاء التثبيت يمسح بيانات التطبيق الخاصة: المفضلة والملاحظات والوسوم والسجل وتقدّم الختمة (مخزنة في SharedPreferences بصيغة JSON بلا نسخ احتياطي) + التلاوات المنزّلة + حزمة ورش. **لا توجد ميزة تصدير في التطبيق حالياً** — لذلك يجب إضافة تصدير/استيراد JSON لبيانات المستخدم في Phase 0 **قبل** تبديل التوقيع، وإعلان إعادة التثبيت للمستخدمين. ولا بديل عن مفتاح جديد: مفتاح debug القديم غير قابل للاستعادة (ضاع مع العدّاء المؤقت)، فالخيار ليس «القديم مقابل الجديد» بل «جديد + إعادة تثبيت» مقابل «البقاء على debug إلى الأبد» (مرفوض من Play وبلا هوية ناشر).

**التوصية الآمنة (لم يُنشأ أي مفتاح في هذه الجولة، كما أمر المستخدم):**
1. توليد keystore جديد دون اتصال على جهاز موثوق (`RSA 4096`، صلاحية طويلة تتجاوز 2033 — يُقترح 25 سنة فأكثر)، باسم ناشر حقيقي لا `Android Debug`.
2. حفظ ملف keystore + كلمات المرور **خارج GitHub تماماً**: نسختان مشفرتان في مكانين منفصلين (مدير كلمات مرور + وسيط دون اتصال)، مع تسجيل البصمات SHA-1/SHA-256 وتاريخ الإنشاء.
3. في CI: إعداد التوقيع يقرأ `key.properties` (مستثنى في `.gitignore` أصلاً) أو متغيرات بيئة، وتُمرَّر القيم عبر **GitHub Secrets فقط** (ملف keystore بصيغة base64 + كلمات المرور + الاسم المستعار) — لا يُلتزم الملف ولا كلمات المرور أبداً، ولا تُطبع في سجلات البناء.
4. اختبار مسار الترقية قبل النشر: تثبيت نسخة debug → تصدير البيانات → إلغاء التثبيت → تثبيت نسخة release → استيراد البيانات والتحقق من سلامتها.
5. **عدم تغيير الـ applicationId** (انظر التصحيح أدناه).

### تصحيح applicationId — تحقَّق منه، وهو يخالف التدقيق والخطة

**الفعلي في APK هو `com.tilawa.app.tilawa` وليس `com.tilawa.app`.** الدليل من `AndroidManifest.xml` الثنائي:
```
package = 'com.tilawa.app.tilawa'
MainActivity = 'com.tilawa.app.tilawa.MainActivity'
permission = 'com.tilawa.app.tilawa.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION'
```
والسبب في `build.yml`: `flutter create --org com.tilawa.app --project-name tilawa` — فلاتر يلحق اسم المشروع بالمنظمة (`org + "." + project-name`). التدقيق والخطة خلطا قيمة `--org` بالـ applicationId. **أي مشروع `android/` حقيقي في Phase 0 يجب أن يستخدم `com.tilawa.app.tilawa` حرفياً** (و`versionName` في APK هو `1.0.0`، و`pubspec.yaml` يقول `version: 1.0.0+1`). تغيير الحزمة أخطر من تغيير التوقيع: يصبح تطبيقاً مختلفاً تماماً بلا أي مسار ترقية.

**حالة هذه النقطة (حسب قرار المستخدم 8):** المفتاح الأصلي غير موجود أصلاً — لا يوجد ما يُستعاد. إنشاء keystore جديد **موقوف** لحين موافقة المستخدم الصريحة على نسخة منفصلة (إعادة تثبيت). لا يُنشأ مفتاح ولا يُغيَّر توقيع في Phase 0.

## 4. خطة ترحيل قاعدة البيانات والنسخ الاحتياطي

**الملفات:** `MIGRATION_PLAN_2026-11-25.md` (الوثيقة الكاملة)، `tools/test_migration.py` (سكربت اختبار الترحيل — Python، مكتبة قياسية فقط، بيانات عينة في `/tmp` فقط). عمل محلي فقط: لم يُدفع شيء، لم تُعدَّل أي ملفات تطبيق، ولم تُمسّ أي DB حقيقية.

### الجرد الموثَّق من الكود الفعلي

**مفاتيح SharedPreferences (لا غيرها — فحص شامل لـ `lib/main.dart` + `lib/db.dart`):**
- إعدادات تبقى في prefs: `mode, font, amiri, reciter, reminder, rem_hour, rem_min, wird_q`
- بيانات مستخدم تُرحَّل: `favs` (StringList آيات بترتيب الإضافة)، `history` (StringList، الأحدث أولاً، سقف 100)، `tags`/`notes` (JSON `{"<ayahId>":"..."}` — وسم/ملاحظة واحدة لكل آية)، `khatmah_q` (int 1..240، والقيمة **241 = الختمة مكتملة**)، `warsh_ready` (bool)، `fav_reciters` (StringList)
- `lib_sha` (String، بصمة مكتبة — يُكتب في `install()` db.dart:372 ويُقرأ في `needsUpdate()` db.dart:378)
- سلوكيات موثّقة تؤثر في التصميم: إلغاء المفضلة يحذف وسمها **ولا يحذف ملاحظتها**؛ `_readMap` يسقط التحميل كله إن كان JSON معطوباً.

**مخطط `quran.db` الحالي** (build_db.py:205–214, 331–333): `meta(key,value)` + `surahs` + `ayahs(id,surah,ayah,text,juz,hizb,quarter,page,sajda)` + `tafsir` (PK ثلاثية) + `ijaz` + `ayahs_fts` (FTS5 unicode61) + 3 فهارس. **لا `user_meta` إطلاقاً، ولا مفاتيح أجنبية.** وملف ثانٍ منفصل `cache.db` فيه `online_tafsir` (يبقى كما هو). `Repo.open()` يفتح `quran.db` للقراءة فقط.

### مخطط الترحيل المصمَّم

**القرار الأساسي: ملف `user.db` منفصل** — لأن `install()` يستبدل `quran.db` كاملاً بإعادة تسمية عند تحديث المكتبة، فأي بيانات مستخدم فيه ستُمحى بصمت. `quran.db` لا يتغير مخططه إطلاقاً.

جداول `user.db` v1: `user_meta(key,value)` وفيها `schema_version='1'` (يبدأ 1؛ الإرث prefs-only هو 0 ضمني) + `lib_sha` (ينتقل هنا من prefs) + `migrated_from_prefs/migrated_at/prefs_backup`؛ و`favorites(ayah_id PK, position, created_at)` + `notes(ayah_id PK, body, updated_at)` + `tags(ayah_id PK, tag, updated_at)` + `history(ayah_id PK, position, visited_at)` + `khatmah(id=1, quarter CHECK 1..241)` + `fav_reciters(reciter_id PK, position)` + `flags(key,value)` لـ `warsh_ready`. الترتيب محفوظ عبر `position`؛ سلامة معرّفات الآيات تُفرض بالتحقق مقابل `ayahs.id` لا بقيد FK (مستحيل عبر ملفين). الترحيلات مرقّمة: `migrate_0_to_1()` للإرث، و`migrate_1_to_2()` محجوزة للمستقبل.

**خطوات `migrate_0_to_1()` (بالترتيب):** قراءة prefs الخام → كتابة النسخة الاحتياطية وإعادة قراءتها ومطابقتها (الفشل هنا يوقف كل شيء والتطبيق يعمل على prefs) → تحليل وعزل التالف في الحجر الصحي → إنشاء `user.db` في معاملة `BEGIN IMMEDIATE` واحدة → **تحقق سجلاً بسجل** (أعداد + ترتيب + محتوى كل وسم/ملاحظة + `quick_check`) → حذف المفاتيح الثمانية المُرحَّلة فقط → سجل ترحيل. القاعدة الذهبية: نسخة احتياطية → معاملة → تحقق → حذف المصدر.

**النسخ الاحتياطي/الاستعادة:** نسخة تلقائية `backups/prefs_backup_YYYYMMDD_HHMMSS.json` (القيم الخام حرفياً + SHA-256، آخر 3 نسخ) قبل أي حذف؛ تصدير/استيراد JSON يملكه المستخدم (`tilawa-user-export` v1) مع تحقق مسبق (dry-run) + نسخة تلقائية قبل الاستبدال + كتابة ذرية (`user.db.tmp` → تحقق → `os.replace`)؛ الاستيراد **يستبدل** البيانات كلياً (لا دمج). الاستبدال الذري للمكتبة يبقى كما هو في `install()` (مؤقت + SHA + إعادة تسمية + إعادة تحقق 6236 آية).

**المسار الوسط (لاحقاً):** خطوط QCF لكل صفحة + بيانات تخطيط = عرض نصي حقيقي مطابق للمطبوع بكسلاً، قابل للبحث والتكبير والتلوين (188MB كاملاً أو ≈310KB/صفحة عند الطلب؛ V4 ≈161MB) — لكنه يحتاج وحدة تسجيل خطوط أصلية + محرك تخطيط 15 سطراً، وحسم قناة الترخيص أولاً.

### التوصية

**نصي أولاً، صور ثانياً كتنزيل اختياري فقط:**
1. **Phase 1 — التخطيط النصي أولاً (كما في الخطة):** مصحف 604 صفحات من `ayahs.page` الموجود في DB — بلا مخاطر ترخيص، <1MB، داخل APK، مع تنقّل الصفحات والعلامات ومزامنة الموضع.
2. **الصور — حزمة اختيارية لاحقة، لا تُضمَّن في APK أبداً:** تنزيل عند الطلب ≈120MB (2600×4206 مضغوطة)، عرض الحجم قبل التنزيل، إيقاف/استكمال، تحقق SHA-256، استضافة على مساحة إصدارات المشروع (نموذج Mihrab). المصدر: توليد ذاتي من خطوط المجمع عبر quran.com-images، أو النسخة الرقمية الرسمية V4 من المجمع.
3. **شروط اعتماد الصور (إلزامية قبل الدمج):** (أ) نسبة واضحة داخل التطبيق: "مصحف المدينة النبوية — مجمع الملك فهد لطباعة المصحف الشريف" + رابط qurancomplex.gov.sa؛ (ب) التطبيق يبقى مجانياً بلا إعلانات وبلا بيع؛ (ج) لا تعديل على الصفحات (لا قصّ ولا إعادة تلوين) ولا عرضها كخلفية زخرفية؛ (د) لا تُستخدم خطوط/بيانات QCF المأخوذة عبر QF API كحزمة دائمة دون إنترنت؛ (هـ) تنزيل اختياري فقط مع خيار الحذف وعرض المساحة.
4. **ما الذي يحتاج إذناً كتابياً:**
   - **يُنصح به بشدة (وليس مطلوباً بالنص المنشور):** طلب تأكيد كتابي قصير من المجمع (عبر qurancomplex.gov.sa) بأن إعادة التوزيع الرقمي المجاني دون إنترنت في تطبيق مجاني بلا إعلانات مشمولة بالاستعمال المجاني — لأن الصفحة الرسمية للشروط حالياً 404، ولأن تدقيقاً مستقلاً اعتبر الحق في شحن حزمة دون إنترنت "غير موثَّق". الرد يُحفظ كسند الترخيص في المستودع.
   - **مطلوب فعلاً:** أي استعمال عبر قناة QF/QUL كحزمة دائمة (ترخيص كتابي منفصل)؛ أي إعادة إنتاج/تعديل لخط KFGQPC Uthmanic Hafs اليونيكود؛ الطباعة الورقية التجارية داخل المملكة (غير مطبقة — التطبيق رقمي مجاني).
   - **لا يحتاج إذناً:** الصور المولّدة من النسخة الرقمية المجانية للمجمع للاستعمال الرقمي المجاني، بموجب الشروط المنشورة — مع التوصية أعلاه كضمان إضافي.

**ما لم يُفعَل:** لم تُنزَّل أي صور أو خطوط، لم يُدمج شيء، ولم يُدَّعَ ترخيص لم يُتحقق منه — والفجوة الوحيدة الباقية هي الصفحة الرسمية للشروط (404)، ويُغلقها طلب التأكيد الكتابي الموصى به أعلاه.

## 6. تصميم PoC محرك التسميع yazinsai في Flutter

**الملف الكامل:** `POC_YAZINSAI_DESIGN_2026-11-25.md`. **الحالة:** تصميم فقط — لا دمج، لا تنزيل نموذج، لا دفع.

**الأساس الموثّق (أُعيد التحقق منه اليوم):** `yazinsai/tilawa` `1.0.0-rc.1`، كود MIT، أوزان 1.x CC BY 4.0 فقط (full 67.8 MB، lite 24.7 MB، مرجع 4.7 MB)، يكشف أخطاء حفظ فقط (لا تجويد/نطق، لا حدر/أطفال، حفص فقط)، دقة 90.3% والتقاط 87.5% **على سطح مكتب M4 فقط** — أداء الهاتف غير مقيس إطلاقاً. المنصات: ويب وNode وRN تجريبي غير مُتحقَّق — لا Flutter أصلي.

### البديل إن فشل yazinsai — Tarteel Whisper + sherpa-onnx (غير مجرَّب)

- **النموذج:** `tarteel-ai/whisper-base-ar-quran` — **Apache-2.0** (موثَّق في بطاقة النموذج ومصادر مستقلة)؛ tiny ≈ 65 MB (WER ≈ 7.05%)، base ≈ 170 MB (WER ≈ 5.75%) — أكبر من yazinsai lite.
- **التشغيل:** حزمة `sherpa_onnx` (pub.dev 2.0.0، Apache-2.0) تدعم Android arm64 رسمياً مع تطبيقات Flutter تجريبية (VAD من الميكروفون + ASR) دون إنترنت.
- **المنطق المرجعي:** مشروع `IqraAI` (MIT) — نسخ بـ Whisper ثم مطابقة وكشف أخطاء (أخضر/أحمر/أصفر)؛ مرجع منطق فقط، فهو تطبيق ويب Gradio (≈500 MB) وليس محرك جوال.
- **الفرق الجوهري:** ليس متدفقاً لحظياً — التغذية الراجعة بعد كل مقطع (ثوانٍ) لا كلمةً بكلمة؛ الطوابع الزمنية للكلمات في sherpa-onnx **تحتاج تحققاً**، والاحتياطي الآمن تغذية على مستوى الآية/المقطع.
- **مستبعَد صراحةً:** `Muno459/fastconformer-quran` وكل أصل Quran-Lab — ترخيص NPL غير تجاري، وقرار المستخدم يستبعدها (أي تبديل إليها = BLOCKED). بديل ثانٍ يُذكر فقط: `mohammed/fastconformer-quran-ar` (CC-BY-4.0، بثّ) — لم تُتحقَّق ملاءمته.

### واجهة PoC المطلوبة

بطاقة حالة نموذج دائمة (غير مثبَّت / جارٍ التنزيل n% / مثبَّت بالطبقة والإصدار والحجم وSHA مختصر / فشل التحميل) ولا تسميع قبل «مثبَّت»؛ تظليل الكلمة الحالية + أخطاء مؤكدة فقط (المشتبه به خافت «محتمل»)؛ نسبة ثقة لكل كلمة/خطأ + شارة حالة التتبع (التقاط/مقفل/غامض/مفقود)؛ **«غير متأكد — أعد المحاولة»** رمادياً لكل `uncertain` أو ثقة < 0.6، والتصحيح الذاتي لا يُحسب خطأً؛ شريط تقدم حفظ بلا درجات؛ لوحة قياسات (زمن التحميل، الخلفية، زمن آخر حدث، تصدير JSONL)؛ وتنبيه صادق ثابت: «مساعد حفظ تجريبي — أخطاء حفظ فقط، لا يقيّم التجويد أو النطق؛ حفص فقط؛ قد يخطئ؛ الصوت لا يغادر جهازك».

### ما تغيّر عن التدقيق (وما لم يتغيّر)

1. **بصفر — توضيح عددي جديد، لا تغيير في الحكم:** التدقيق لم يذكر عدداً لبصفر؛ Maqra توثّق الآن 6314 ملفاً (6236 آية + 78 بسملة فقط، أي 36 سورة بلا ملف `SSS000`)، و«0 آية غائبة». هذا لا يؤثر على التشغيل آيةً بآية (التطبيق يستخدم `SSSAAA` لا `SSS000`)، لكن تحقق MD5 لبصفر هو **0** (لا توجد قائمة MD5 أصلية من EveryAyah لهذا المجلد) — أي أن تحققه أضعف من بقية القرّاء (بايت-بايت فقط). يبقى مكتملاً.
2. **الحصري والمنشاوي في islamic.network — قيد جديد لم يذكره التدقيق:** فحص risan (2026-10-01) يفيد بأن `ar.husary` و`ar.minshawi` فيهما **6235 آية لا 6236** (آية واحدة غائبة في كلٍّ منهما، دون تحديد أي آية). لم يُتحقق مستقلاً من الآية الغائبة. التوصية: **EveryAyah أولاً لهذين القارئين** حتى تُحدَّد الآية الغائبة بفحصٍ في Phase 2؛ ولا يُجعل islamic.network مصدراً أولاً لهما قبل ذلك.
3. **نوع الإصدار في API لـ المنشاوي وعبد الباسط — شذوذ يُفحص لا حكم اكتمال:** القائمة الحية اليوم تسجّل `ar.minshawi` و`ar.abdulbasitmurattal` بنوع `translation` لا `versebyverse` (بينما risan يعاملهما كإصدارين آيةً بآية ويتحقق من روابط CDN لهما). لا يُستنتج من ذلك نقص؛ يُفحص في التطبيق بطلب الآيتين 1 و6236 من CDN قبل الاعتماد عليهما كاحتياطي.
4. **أسماء المجلدات/الإصدارات — كلها ما زالت صحيحة** في `recitations.js` الحي، مع تدقيقات إملائية يجب الالتزام بها حرفياً في الكود: المنشاوي يُكتب `Minshawy` لا `Minshawi` (`Minshawy_Murattal_128kbps`)؛ المعيقلي 128 بلا شرطات سفلية (`MaherAlMuaiqly128kbps`، خلافاً لمجلد 64 `Maher_AlMuaiqly_64kbps`)؛ العجمي بحروف صغيرة (`ahmed_ibn_ali_al_ajamy_128kbps`) — وله بديلان آخران في EveryAyah يجب عدم الخلط بهما.
